# sbx 对话式项目配置 Skill 设计

状态：首版 skill、知识校验工具与发布集成已实现；真实模型对话、Docker 和私网验收待完成。未新增 sbx CLI 能力。  
代码校对日期：2026-11-09。  
拟安装位置：`sbx_skills/sbx-configure/`。

## 1. 目标与使用体验

用户在项目目录中对 agent 说“帮这个项目配置 sbx”，skill 调查项目，询问无法从代码确定的依赖与使用偏好，生成或更新配置，并按授权范围验证。

最终交付应回答四个问题：这个项目在 task 内能做什么；用了哪些工具、服务与网络；改了哪些文件；哪些行为已经验证、哪些仍待验证。

支持三类请求：

- 初始化：“这个 Go 项目需要编译和跑测试，帮我配置 sbx。”
- 调整：“改用 Codex，再加一个测试用 Redis。”
- 排障：“prep 成功了，但 task 里还是下载依赖，帮我查一下。”

第一版以现有 sbx CLI 和文件配置为基础，不要求新增服务、后台进程或专用协议。CodeGraph 可辅助大型项目调查，但不作为运行前提。skill 可由宿主机上的配置 agent 使用；不能假设当前沙箱内的 agent 能管理宿主机 Docker 或修改宿主机配置。

## 2. 设计原则

1. 先调查已有事实，再询问使用意图。发现数据库客户端不等于已经确定需要数据库服务。
2. 问题围绕“需要完成什么工作”，由 skill 将答案映射到 profile、prep、services、forward 等机制。
3. 项目配置表达共享需求，本机配置表达具体地址、认证来源与机器差异。
4. 保留已有配置与用户修改，只改变本次需求涉及的字段，不自动升级其他依赖或 agent 版本。
5. 交付真实验证结果。语法有效、构建成功、容器可运行和项目测试通过分别记录。
6. 缺少必要信息时先完成独立部分，留下明确阻塞项，不生成看似完整的虚假值。

## 3. 范围

### 第一版包含

- 检测语言、工具链、依赖管理方式、工作区结构与常用命令。
- 选择 agent、profile 或用户已有镜像。
- 生成 `.sbx/sandbox.toml`，必要时生成 `.sbx/prep.Dockerfile`。
- 为私有依赖配置 BuildKit secret 的 ID 与本机映射方案。
- 配置临时伴生服务、运行期网络，以及本机 forward 方案。
- 检查忽略文件、依赖 volume、缓存与 task 入口的关系。
- 增量修改、展示差异，并验证配置及用户选定的项目命令。

### 暂不包含

- 自动申请或获取公司账号、密钥、VPN 权限。
- 自动访问生产数据库、导入真实数据或执行数据库迁移。
- 将任意 Compose 文件完整转换成 sbx services；不支持的能力应说明。
- 自动实现 sbx 目前不存在的挂载、secret 注入、健康检查等配置字段。
- 替用户修改业务代码以掩盖环境问题；业务代码修改需要符合本次请求范围。

## 4. 对话流程

### 4.1 调查并给出简短摘要

优先读取依赖清单、锁文件、语言版本声明、Makefile、CI、Dockerfile、Compose、开发文档与已有 `.sbx` 配置。检查本机 sbx 的实际版本和相关命令帮助，避免只按 skill 内置知识生成配置。

不遍历依赖目录或读取凭据内容。环境文件优先读取示例文件与变量名，报告中不输出实际密钥。

调查摘要示例：

> 已确认：Go 版本来自 go.mod；CI 执行 make test；测试配置引用 PostgreSQL。待确认：测试使用临时数据库还是已有开发库；运行期间是否还要访问公司 API。

内部可以用如下信息表组织推理，不要求写成新的持久化数据格式：

| 项目 | 内容 | 证据或来源 | 状态 |
|---|---|---|---|
| 工具链 | Go，具体版本以当前文件为准 | go.mod | 已确认 |
| 测试命令 | make test | CI / Makefile | 已确认 |
| 数据库用途 | 临时测试库或已有实例 | 等待用户 | 待决定 |
| 网络 | 是否需要公司 API | 等待用户 | 待决定 |

### 4.2 询问缺失信息

每轮聚焦一组相关决策，通常提供两到三个选项及推荐理由。已经从文件确认的事实不重复询问。用户明确的选择保留在本次修改中，不要求每次重新回答。

提问优先级：使用目标 → 影响方案的依赖选择 → 网络和认证来源 → 验证范围。资源参数等可根据已有设置或默认值处理，并在方案中说明。

例如数据库选择：

> 集成测试需要 PostgreSQL。建议创建独立测试库，数据随任务生命周期管理。你要选临时实例，还是连接已有开发库？

涉及认证时询问本地凭据文件路径或环境变量名称，不询问密钥正文。

### 4.3 给出具体方案并写入

先说明工具链、依赖准备、运行服务、网络访问、预计修改文件和验证命令。用户已经要求配置的项目内可逆修改直接完成；不要为了常规字段反复增加确认步骤。

本机配置写入、Docker 构建、访问已有外部服务等操作遵守本次授权和执行环境权限。尚未授权的动作先准备好具体差异与命令，再请求相应授权。仅想查看方案时不启动构建或 task。

### 4.4 验证并交付

按第 8 节分层验证，展示最终差异及未完成事项。如果环境没有 Docker，仍可完成配置草案与可执行的后续验证步骤，但不能标记“环境已可用”。

## 5. 配置决策规则

### 5.1 配置层与合并

| 信息 | 放置位置 | 处理要求 |
|---|---|---|
| 默认 agent、profile / image、资源限制 | 项目层可表达 | 避免无意义地写满默认值 |
| deps.mask、prep.watch、prep.secrets | 项目层 | secret 只写 ID；watch 覆盖真实构建输入 |
| 临时 services | 项目层 | 使用当前支持的 name、image、port、env |
| 运行期网络模式、允许域名、非敏感 env | 项目层可表达 | 检查实际合并结果和字段限制 |
| Agent 认证来源、prep.secret 文件路径 | 全局层或工作区层 | 项目专属需求优先采用工作区层 |
| forward、隔离策略、安全开关 | 全局层或工作区层 | 不写进项目文件 |
| prep.on_drift | 全局层或工作区层 | 不为方便运行而擅自启用自动构建 |

当前基础层顺序是内置默认值 → 全局 `~/.sbx/config.toml` → 项目 `.sbx/sandbox.toml` → 工作区 `~/.sbx/workspaces/<ws>.toml`，此外 prep 声明和组织约束也可能影响结果。工作区 ID 应通过当前 sbx 行为取得，不能自行猜测。

列表存在并集合并语义，services / forward 按 name 合并。删除项目文件中的某一项不保证消除其他层的同一需求。必须检查最终生效值和来源；当前机制无法表达的收缩操作应明确说明。

### 5.2 依赖与网络

| 用户需求 | 优先方案 | 验证重点 |
|---|---|---|
| 下载私有包 | prep + BuildKit secret | 构建可下载，凭据未复制进镜像产物 |
| task 使用安装好的包 | prep 播种依赖 volume / cache | 安装路径与播种路径一致 |
| 独立 PostgreSQL / Redis | services | 使用服务名访问；等待实际就绪 |
| 已有宿主机 / 内网服务 | 本机 forward | 具体地址与端口、访问用途、容器内可达性 |
| 外部 HTTP API | 运行期 network 配置 | 模式、域名规则、代理、TLS 与业务响应 |
| 特殊系统工具链 | 合适 profile 或自定义 image | 工具实际存在且版本满足项目 |

当前默认网络模式是 open。skill 不应声称默认已经启用 allowlist，也不应在排障时未经用户意图直接扩大网络范围。allowlist 放行不代表目标可达；prep 构建网络与 task 运行网络需分别诊断。

prep 只播种 WORKDIR 下命中 deps.mask 的目录，以及 `/sbx/cache/*` 下的一级目录。使用自选基础镜像时必须显式检查缓存环境变量；不能假设普通语言镜像已经具有 sbx agent 镜像的缓存布局。安装进 `/usr/local` 的系统工具也不会仅凭 prep 自动出现在 task 中，应使用合适的运行镜像。

watch 应覆盖锁文件、参与 COPY 的清单、证书或安装辅助文件等实际输入。某个文件不参与构建时，不为凑齐模板而添加。monorepo 要检查嵌套路径、workspace 清单和本地依赖。

### 5.3 文件可见性与构建上下文

`.gitignore` 不构成容器挂载过滤规则。main task 通常挂载原仓库；独立 task 使用独立 worktree，不能假设拥有原仓库中的忽略文件。deps.mask 会覆盖对应容器路径，不是通用的敏感文件隐藏功能。

遇到本地数据、模型或配置文件时，应询问用途和需要使用的 task 入口，再检查当前机制是否支持。不要生成不存在的任意 bind mount 字段，也不要为了可见性直接将敏感文件加入 Git。

prep 的构建上下文是仓库根。生成 COPY 指令和 Docker 忽略规则时应保留已有行为、控制必要输入，避免 COPY 整个仓库；不能把 `.gitignore` 当成 Docker 构建排除规则。

## 6. 产物与 Skill 结构

最小结构：

```text
sbx_skills/sbx-configure/
├── SKILL.md
└── references/
    ├── config-rules.md
    └── prep-network.md
```

SKILL.md 保存触发条件、调查与对话流程、交付标准，引用相关参考文件。参考文件只记录 sbx 特有约束，避免复制整份 CLI 手册。第一版不预建通用扫描器；出现重复且需要确定性执行的处理后，再增加小型脚本。

项目产物按需创建：`.sbx/sandbox.toml`、`.sbx/prep.Dockerfile`，以及必要的非敏感辅助输入。默认通过最终回复交付摘要；仅在用户需要团队复用说明时增加项目文档，避免每次运行都制造报告文件。

`sbx_skills/` 是本仓库的 skill 源码位置。仅将文件放入该目录不保证调用方 agent 自动发现；后续实现应说明目标 agent 的加载方式，不擅自修改用户全局 skill 安装。

## 7. 具体场景

### 场景 A：公开依赖的 Go 项目首次接入

**用户：**“帮我配置 sbx，用 Codex，能跑单元测试即可。”

**调查：**从 go.mod 和 CI 确定版本及测试命令，检查已有 profile 能否满足工具链。若依赖全公开且无预装要求，不因存在 go.mod 就强制创建 prep。

**对话：**仅在工具链不匹配、测试依赖外部服务等影响方案时追加问题。

**产物：**按需设置 default_agent 和运行环境。认证已可用时复用；缺失时给出本机认证设置步骤。

**验收：**在选定 task 入口内检查 Go 版本，执行确认过的单元测试命令。只通过配置检查时，不能声称测试通过。

### 场景 B：Go 私有依赖需要公司网络

**用户：**“Go 包在公司 GitLab，宿主机能下载，task 里不行。”

**调查：**检查模块域名、GOPRIVATE、replace、本地模块路径与现有依赖安装方式。

**对话示例：**

> Agent：公司 GitLab 只用于下载依赖，还是 task 运行中也需要调用？
> 用户：只下载包。
> Agent：采用 prep 固化依赖。现有认证使用 netrc、SSH，还是其他方式？请提供方式或文件路径即可。

**产物：**适配实际认证方式的 prep Dockerfile；项目层声明 watch 和 secret ID；本机层映射凭据文件。缓存目录应与 task 播种契约一致。不把 SSH 认证假装成 netrc 方案。

**验收：**prep 下载成功；新 task 内模块缓存可用；执行选定编译命令时不再需要私有凭据。实际离线验证与“命令成功但未观察下载行为”分别报告。

### 场景 C：Node 项目需要 PostgreSQL 和 Redis

**用户：**“帮我把集成测试环境配好，数据库每个任务独立。”

**调查：**读取锁文件、CI 服务版本、应用环境变量示例及测试初始化过程。

**对话：**确认数据库版本、是否允许创建测试数据、初始化命令。已有 CI 信息可作为推荐依据，不直接沿用未确认的真实数据库地址。

**产物：**依赖目录 mask，按需生成 prep，添加 db / redis services，配置应用实际支持的非敏感连接参数。使用 `db:5432` 等服务地址，不能把容器内 localhost 当作伴生服务地址。

**验收：**依赖可用，两个服务实际就绪，测试初始化和集成测试通过。services 当前没有健康检查字段，不能生成 healthcheck 配置；就绪验证使用外部探测或项目现有测试机制。

### 场景 D：连接本机已有开发数据库

**用户：**“不要新建库，用我电脑上的 5432。”

**对话：**确认这是允许连接的开发实例，明确只检查连通性还是运行会写数据的测试。沿用用户已经给出的用途授权，不重复询问同一事项。

**产物：**在本机工作区层生成指向宿主机 5432 的 forward 配置，按实际应用设置连接地址。项目共享文件中不写具体 forward；应用认证通过当前支持的本机机制安排。

**验收：**先验证 TCP / 数据库握手与认证。只有已授权写入测试数据时才运行相应集成测试；仅端口可达不能称为数据库测试通过。

### 场景 E：公司 API、代理和私有 CA

**用户：**“task 要调用一个 HTTPS 内网 API，还需要公司证书。”

**调查与对话：**确认实际域名、端口、证书来源、宿主机访问路径，以及这是构建期还是运行期需求。检查 TLS 域名与 SNI，不能简单将 URL 替换成转发别名导致证书不匹配。

**产物：**按实际路径选择运行期网络或本机 forward；使用当前支持的 CA 交付方式。证书与私钥分开处理，不将私钥当作可提交 CA 文件。代理配置也区分构建和 task 两个阶段。

**验收：**分别记录解析、TCP、TLS 和最小业务请求的结果。不以关闭 TLS 校验作为完成条件。

### 场景 F：被 Git 忽略的模型或数据目录

**用户：**“项目有个没提交的 models/，task 需要读取。”

**对话：**询问文件体积、是否敏感、只读还是写入，以及使用 main 还是独立 task。

**产物：**先解释选定入口的文件可见性。main 场景检查真实挂载与 mask 冲突；独立 worktree 场景说明当前不会自动复制这些文件，提出符合现有能力的数据准备方式。没有适用机制时列为能力缺口，不伪造配置完成。

**验收：**在目标 task 内检查路径与最小读取操作。不能用宿主机上存在文件作为容器可读的证据。

### 场景 G：已有配置增加 Redis，并切换 agent

**用户：**“保留现有环境，改用 Codex，再加 Redis。”

**调查：**读取各层配置及来源，检查同名服务和已有认证来源。

**产物：**只修改本次相关字段。若已有同名 redis，比较后更新该服务，避免重复追加。没有新的构建依赖时不重写 prep。展示被更高优先级本机配置覆盖的项目设置。

**验收：**最终生效 agent 为用户选择，Redis 服务可访问。第二次执行同一请求不新增重复条目或产生无关变更。

### 场景 H：prep 成功，task 中仍缺依赖

**用户：**“构建成功了，但启动 task 还是提示找不到包。”

**诊断：**依次核对安装输出目录、WORKDIR / deps.mask / 缓存变量、watch 漂移、镜像 tag，以及目标 task 是否使用了新种子。先用这些证据定位，不默认扩大网络或重新安装所有依赖。

**产物：**只修改已确认错误的路径或构建输入配置。若旧 task 需要 reseed，说明其会覆盖依赖 volume；在相应授权下执行，或用新 task 验证。

**验收：**目标容器内能找到所需依赖，并执行原失败命令。报告是哪一环修复及验证依据。

### 场景 I：Monorepo，当前目录只是子项目

**用户：**“只配 apps/api，不需要前端。”

**调查：**识别 Git 根、子项目路径、根级 workspace / lockfile 和共享库，检查子项目能否单独安装。

**产物：**项目配置仍位于仓库约定位置，prep COPY、watch、mask 使用正确相对路径。若根级安装会包含前端，解释原因与可选方案，不静默扩大范围。

**验收：**在正确目录执行 API 的命令，修改实际构建输入能触发预期漂移。

## 8. 验证与完成标准

| 层次 | 方法 | 可以得出的结论 |
|---|---|---|
| 配置 | 当前 CLI 加载配置，检查错误、未知字段警告与来源 | 配置被当前版本接受 |
| 合并结果 | `sbx config show`，核对是否遗漏 prep 声明或组织约束 | 已观察范围内的生效配置符合意图 |
| 构建 | 按需执行 `sbx prep build --check` | 构建及报告完成，尚不等于 task 已播种 |
| 容器环境 | 选定入口的新 task 内检查工具链、文件和依赖 | 该 task 的实际环境可用 |
| 服务与网络 | 最小连接、TLS 或服务探测 | 目标能力在当前环境可用 |
| 项目行为 | 约定的一条编译、测试或启动命令 | 该命令在目标环境通过 |

`sbx prep build --check` 会实际构建，不是静态 dry run。`sbx config show` 可能检查 daemon 隔离并尝试读取 prep 镜像声明，存在依赖不可用时的提示；不能忽略这些提示并宣称完整验证。

最终交付包含：变更文件与目的、关键选择、验证命令及实际结果、未验证项与后续动作。状态使用已通过、失败、阻塞、未执行、不适用；不要把生成文件记为运行成功。

## 9. Skill 自身的验收

实现后以临时项目夹具进行行为验证，涉及真实 Docker 的部分单独标记：

| 用例 | 验收点 |
|---|---|
| 公开 Go 项目 | 能利用清单与 CI，避免重复询问已知信息 |
| 私有依赖 | secret ID 与路径分层正确，缓存可播种 |
| services / forward | 临时服务与已有实例选择正确，不生成不支持字段 |
| 已有配置 | 增量修改保留其他字段、注释和用户改动 |
| 重复调用 | 相同需求不重复追加服务或列表 |
| 高层覆盖 | 能发现用户选择未实际生效，并解释来源 |
| 无 Docker / 无 sbx | 给出具体阻塞项，仍交付可完成的方案 |
| 忽略文件 / monorepo | 使用实际 task 入口和路径语义判断 |
| prep 故障 | 能区分构建、播种、旧 task 与运行期问题 |

先做 SKILL.md 格式校验，再检查上述行为；格式校验不能替代真实配置与运行验证。

## 10. 实现顺序与可选扩展

1. 实现调查、提问、增量写入及配置检查，覆盖 A、D、G、I。
2. 实现 prep、services、网络诊断，覆盖 B、C、E、H。
3. 在具备 Docker 的环境验证完整流程，覆盖 F 的文件可见性边界。

后续可以增加“检查项目变化并更新环境”的维护模式：依据锁文件、CI 或工具链变化提出最小变更；只有用户请求维护时才执行，不引入后台自动修改。

如果实践证明 CLI 的机器可读信息不足，再讨论配置检查、字段来源、工作区标识等专用 JSON 输出。这些属于后续 sbx 能力，不在第一版 skill 中虚构命令。

## 11. 功能知识来源与生命周期

采用“随版本发布的知识包 + 使用时的本机能力探测”。知识不依赖模型记忆，也不要求目标项目包含 sbx 源码。离线时仍可使用匹配本机版本的知识包。

### 11.1 知识从哪里来

| 来源 | 用途 | 边界 |
|---|---|---|
| 本机 `sbx version --json` | 应用版本、协议及声明能力 | 不保证穷举所有配置功能；旧版本可能不支持 |
| 相关命令的 `--help` | 命令、参数及默认值 | 不足以描述配置合并和运行语义 |
| 本机 `sbx schema` 返回的列表与 schema | 对相应协议输入做结构校验 | 不能假设存在 sandbox.toml 的完整 schema |
| 随版本发布的 references | 配置分层、prep 播种、网络边界等语义 | 必须有版本身份与行为验证 |
| 项目文件和生效配置 | 当前项目需求、配置来源 | 不能代替工具契约 |
| 受控运行结果 | 当前环境的实际行为 | 结论限于对应 task、输入与当时环境 |

命令语法以本机帮助为依据；帮助未覆盖的语义使用匹配版本的知识与验证。来源冲突时明确核对，不静默选取。源码只有能对应目标构建时才可作为版本证据；任意网上最新版文档不能替代旧版本契约。

### 11.2 知识包身份与刷新

已增加 `knowledge-manifest.json`，记录知识包修订号、适用 sbx 版本、对应源码提交、来源文件、审核时间、内容摘要和验证范围。这是 skill 元数据，不是 sbx CLI 协议；实际场景结果见验收记录。

第一版采用精确配套发布，实际验证多个版本后再声明兼容范围。每次使用时识别实际二进制路径和版本，探测本次相关命令。版本匹配且能力可用时使用参考知识；未知或不匹配时继续项目调查和方案准备，暂停依赖未知语义的动作。

优先取得目标版本配套的知识包；离线或无法取得时明确列出无法确认的部分，不拿最新版知识直接生成未知字段。获取远端资料遵守当前网络权限。

版本、二进制内容、相关帮助或知识包变化触发重新核对。统一显示 dev 的构建不能只比较版本字符串，应结合二进制摘要、可取得的源码构建信息；无法建立对应关系时按未知构建处理。时间戳用于追溯，固定天数不能保证兼容性。

### 11.3 数据各自的有效范围

| 数据 | 有效范围和失效条件 | 保存方式 |
|---|---|---|
| 工具语义 | 对应版本 / 构建；升级或知识包变化后重核对 | 随 skill 发布，不含用户数据 |
| 命令探测缓存 | 对应二进制身份；替换或升级即失效 | 第一版仅会话内即可 |
| 项目调查 | 对应清单、锁文件、CI 和配置内容；变更后重查相关部分 | 第一版不新增长期数据库 |
| 用户选择 | 对应项目需求；用户最新明确指令优先 | 用配置及必要注释表达 |
| 本机配置 | 对应机器与工作区；修改前重新读取 | 留在原配置层，不复制到知识包 |
| 验证证据 | 对应 task、命令、输入与环境 | 交付摘要；复用前判断是否需复验 |
| 凭据 | 不属于知识缓存 | 不复制内容，仅使用获授权的来源引用 |

skill 更新不自动重写用户项目配置。版本相同也不能证明外部服务、认证、网络和本机路径仍然有效。当前设计不新增持久化探测缓存，因此第一版无需额外的缓存清理服务。

### 11.4 谁负责更新及如何保证

sbx 功能维护者负责同步修改受影响的 references 和验收场景；发布时将知识包绑定到同一源码提交。发布流水线应检查清单身份、引用、相关行为测试，并使用待发布二进制校验命令文档。已有 `core/scripts/check-wiki-cli.py --sbx <binary>` 可检查 CLI 参考与实际帮助是否一致。

命令参考可以自动生成；配置合并、挂载、播种等语义需要维护者结合代码与行为测试整理。仅靠 help 或版本号不能保证这些语义正确。知识包、失效检查与 CI / 发布封包集成已实现，见 `sbx_skills/sbx-configure/`；本地已验证脚本及真实 CLI 夹具，托管 CI 和真实运行场景仍需实际执行。

### 11.5 功能迭代时的同步流程

sbx 功能和 skill 在同一个 PR 中迭代，随同一次发布交付。维护者负责语义审核；自动检查负责发现漂移和验证可确定的行为，不能代替审核。

| sbx 变化 | 同步更新内容 |
|---|---|
| 配置字段、默认值、分层或合并规则 | config-rules、条件式提问、生成示例、配置夹具 |
| CLI 命令、参数或默认值 | 调用指引、帮助摘要、CLI 参考及相关测试 |
| prep、服务、网络、文件可见性 | prep-network、决策与排障流程、对应场景验收 |
| 仅内部重构 | 核对语义是否保持一致，记录无需改写参考知识的理由，并更新源码绑定 |
| 仅修正 skill 指引 | 更新参考知识及修订号，保持二进制适用范围，不擅自扩大兼容声明 |

执行顺序：

1. **评估影响。** 功能作者在 PR 中说明受影响的用户需求、skill 文件和验收场景；认为无需修改指引时说明依据。
2. **同步修改。** 在同一 PR 更新实现、参考知识、示例和测试，保留旧项目配置的迁移说明。新增字段不能只出现在代码或 help 中。
3. **构建与验证。** 从目标源码构建 sbx，运行脚本与配置夹具、CLI 文档一致性检查，以及变更涉及的实际行为验收。缺少 Docker 或私网时明确记录未验证范围。
4. **审核并绑定。** 维护者审核语义和证据后递增 knowledge_revision，执行 seal，再检查 check / probe。当前 seal 要求相关 core 变更已经提交，因此可在同一 PR 内先提交功能，再提交知识清单；无需拆成两个 PR。
5. **CI 与发布。** CI 检查知识完整性、源码漂移和受控行为。发布流程按最终目标构建重新绑定各平台归档摘要，配套生成 skill 包；交叉编译不算各平台运行验收。
6. **用户升级。** 用户获取配套二进制和完整 skill 包，调用时重新 probe。缺少匹配知识时保留调查结果并提示缺口，不自动 seal、升级二进制或重写项目配置。用户请求迁移后，才做增量修改和相关复验。

维护者在仓库根执行的核心命令：

```sh
SBX_SKILL_TEST_BINARY=<binary> python3 core/scripts/test-configure-skill.py
python3 core/scripts/check-wiki-cli.py --sbx <binary>
python3 sbx_skills/sbx-configure/scripts/knowledge.py seal \
  --sbx <binary> --repo . --revision <新修订号> --reviewed
python3 sbx_skills/sbx-configure/scripts/knowledge.py check --repo .
python3 sbx_skills/sbx-configure/scripts/knowledge.py probe --sbx <binary>
```

若测试中的封包检查因旧清单的源码摘要变化而失败，应先完成源码/参考知识审核及必要的专项测试，再 seal，并重新执行整套检查。不要为让 CI 变绿直接刷新摘要；seal 不产生缺失的行为证据。

建议每个相关 PR 附以下说明，目前它是文档约定，尚未新增强制 PR 模板或自动语义审核：

- [ ] 已说明 skill 影响，或给出无需修改指引的理由。
- [ ] 已同步相关规则、示例、测试及知识修订号。
- [ ] 已记录通过、失败和未执行的场景及证据。
- [ ] 已检查知识绑定与目标二进制，未借 seal 放行未审核语义。
- [ ] 已说明升级影响、迁移方式与可用的配套版本。

具体安装、重新绑定和封包说明见 [Skill 维护说明](../sbx_skills/sbx-configure/references/maintenance.md)。
