01

A day of real use

One runtime, three ways to use it. Choose a scenario to follow its workflow.

Select a scenario above. All commands shown are existing CLI entry points; deployment prerequisites differ.

09:30

Three unrelated jobs, all started at once

Fix a login bug, add search, bump a dependency. You used to queue them up, because all three touch the same repo.

$ cd ~/code/shop
$ sbx run fix-login            # go in, explain the job, Ctrl-b then d to leave
$ sbx run add-search --detach  # this one starts in the background
$ sbx run bump-deps --detach

Each task gets its own worktree, branch and container. They are separate at the filesystem level, not by convention, so edits do not share a working tree. This is not an adversarial boundary between users with Docker API access.

10:00

A glance before the standup

$ sbx ls
workspace shop-e76272 (/Users/you/code/shop)
TASK        STATUS   BRANCH          AHEAD  DIFF         LAST-ACTIVE
add-search  running  sbx/add-search  0      2f +86 -3    4s ago
bump-deps   idle     sbx/bump-deps   1      1f +12 -12   6m ago
fix-login   running  sbx/fix-login   1      3f +48 -6    11s ago

bump-deps has been quiet for six minutes — either it finished, or it stopped to ask you something. Go look.

11:00

Review one of them

$ code "$(sbx path fix-login)"   # the worktree is a real directory on your host

Not happy? Attach and keep talking. Happy? Wrap it up.

14:00

A task needs MongoDB and the network blocks it

$ sbx net denied
HOST                 COUNT  LAST    KIND            TASK
fastdl.mongodb.org   4      2m ago  not allowed     shop-e76272.add-search

$ sbx net allow fastdl.mongodb.org
Added to ~/.sbx/config.toml: fastdl.mongodb.org
Hot-reloaded into 3 running tasks; no restart needed

There is a record of everything the agent reached for. Once the permission prompts are off, that record is the thing that lets you relax.

15:30

The backend tests want a database

# shop/.sbx/sandbox.toml — safe to commit: no address, no credential, no host path
[[services]]
name  = "db"
image = "postgres:16"
port  = 5432
env   = { POSTGRES_PASSWORD = "dev" }

$ sbx run api-rate-limit
service db: postgres:16, reachable in the task as db:5432

The failure you are avoiding is not the error message. Unattended, the agent does not stop to ask: it tries apt-get install postgresql (no root), tries docker run (no socket), and then starts editing the tests to work around the database — and hands you a branch where everything passes.

The service container sits on the task's --internal network, so this costs no egress route at all. It is reached by its name, not localhost: it is a different container.

16:20

…and half the dependencies live on an internal registry

$ sbx prep build
built sbx/prep-shop-e76272:a1b2c3d4e5f6

$ sbx run add-sdk
seeding cache/go-mod from sbx/prep-shop-e76272:a1b2c3d4e5f6 (184MB) ...

The obvious move — give the sandbox intranet access — is the expensive one: the credentials go in with it. So the fetching moves to the host instead. One docker build where you still have the network and the credentials; the result is seeded into each new task's volumes.

The credential is a BuildKit secret: alive for one RUN, absent from every layer. The task itself never connects to the intranet once.

18:00

End of day

$ sbx stop fix-login    # shut it down; container and conversation are kept

Tomorrow, sbx run fix-login picks the conversation back up where it stopped.

Next day

Wrap up

$ sbx done fix-login          # container, network, dep volume, worktree — branch stays
$ git merge sbx/fix-login     # you merge; sbx never does it for you
$ git branch -D sbx/fix-login
SETUP

Share the task contract, keep identities separate

A team agrees on a report format, completion criteria and TaskSpec in version control. Each member has their own provider identity, local resource grants and dedicated Docker daemon. An administrator installs organization ceilings through a trusted channel.

# Each member checks their own environment
sbx isolation status --json
sbx login codex --status
sbx policy show

Project files describe requirements; they do not grant access. Local execution-policy.toml entries bind source, verifier and delivery references to resources approved for that member. Mutually untrusted users need separate daemons or VMs.

09:30

Run the same declared workflow under team policy

The team has prepared report-task.json and registered its source, completion rules and local delivery target. Managed execution uses synchronous TaskSpec, including Git Source for code tasks.

sbx admit --spec report-task.json
sbx task run --spec report-task.json
sbx task status monthly-report --json

Organization limits intersect personal grants. Admission is checked again during execution; updating, revoking or expiring policy cancels the supervised activity. This workflow does not enable managed interactive or detached sessions.

11:00

Review the retained artifact, then deliver

A manual criterion leaves the task in needs_review. An authorized operator inspects the immutable snapshot and validation evidence before recording a decision. The reviewer label records that decision; authentication and role assignment remain deployment responsibilities.

sbx task status monthly-report --json
sbx task approve --spec report-task.json --reviewer alice
# If the delivery needs reconciliation, continue without rerunning the agent
sbx task deliver --spec report-task.json

Approval and delivery reuse the original attempt. The Sink is a registered local directory or local Git target; there is no implicit remote push, merge or shared review dashboard.

16:00

Export team events without exporting business payloads

Managed lifecycle events first enter a private durable outbox. With a configured collector endpoint and a private per-member token, members or an external operator process can explicitly flush the queue.

sbx events status
sbx events flush

The collector is supplied by the deployment. It authenticates organization and subject, deduplicates stable event IDs, and acknowledges durable storage. Offline delivery is retried with the same IDs; raw prompts, full results and tool payloads are not team-event fields.

BUILD

Embed sbx behind an existing automation system

A CI job, service or scheduler invokes the local CLI on a worker host with an assigned daemon. sbx supplies the execution boundary and durable task facts; your caller owns queuing, job placement, credentials and lifecycle supervision.

sbx version --json
sbx schema task > task.schema.json
sbx schema event > event.schema.json
sbx admit --spec job.json

Inspect capability requirements as well as schema shape. Valid JSON does not authorize resources, and admission does not reserve capacity. sbx does not provide a resident worker service or a multi-tenant control plane.

SUBMIT

Capture a synchronous run and its actual exit code

The caller creates job.json from an approved template, with a stable logical task ID and registered resource references. Keep stdout machine events separate from diagnostics.

run_code=0
sbx task run --spec job.json > execution.jsonl 2> execution.log || run_code=$?
# Preserve run_code; inspect execution, validation and delivery separately
sbx task status job-42 --json

Here job.json declares task_id=job-42. An agent exit of zero is not sufficient evidence of business completion. The caller must interpret the process exit code and the final result, then route needs_review, delivery failures and unknown operations appropriately.

RECOVER

Continue retained facts after interruption

If the submitting CLI dies, first inspect the record. Recover an orphaned execution before deciding whether to continue verification, reconcile a receipt, deliver a snapshot or explicitly start a new attempt.

sbx task status job-42 --json
# Only for an orphaned execution; use task stop for a live supervisor
sbx task recover job-42
# Choose the next command from recovery guidance, not a blanket retry loop
sbx task reconcile --spec job.json

Reconcile is query-only for unknown writes. Never switch task IDs or delete records to bypass a pending effect. Missing input baselines and damaged records can still require manual investigation; recover does not fabricate success.

RELEASE

Reclaim runtime resources independently of results

Once the activity is closed, reclaim its dedicated containers, network and dependency volumes while retaining the workspace, logs, snapshots and receipts. Keep artifact retention an explicit policy.

sbx task clean job-42
# A retained artifact can still be verified or delivered
sbx task deliver --spec job.json
# Once reconciled, explicitly prune a selected snapshot if appropriate
sbx task prune job-42 <attempt-id>

Cleanup does not erase unknown outcomes or authorize replay. A new run creates a new attempt under current grants. Remote artifact publication, central scheduling and a production collector must be integrated separately.

02

Why it is built this way

The whole thing starts from one trade-off.

A coding agent only gets out of your way once you turn the permission prompts off — and the moment you do, it can touch anything on your machine.

Doing that on your host machine has four concrete risks. sbx turns one unit of agent work into a Task and answers each risk with one measure.

① WHERE CHANGES GO

Code

It wrecks the working tree you are using right now.

Its own git worktree and branch
② WHERE IT RUNS

Runtime

It reads ~/.ssh, or leaves installed junk on your host.

A container with controlled mounts
③ WHAT IT REACHES

Network

It talks to anything — leaking data or pulling in a bad dependency.

An internal network behind a proxy
④ STAYING IN CONTROL

State

You come back and cannot tell how far it got.

Hook-written state, ls, memory sync

The lifecycle run → stop → run (resume) → done creates, pauses, restores and tears down all four together.

sbx itself is only an orchestrator: a single Go binary that does everything by shelling out to docker and git, with no SDKs. It has no resident daemon: detached commands return while the agent keeps running; a foreground headless caller waits for its result.

03

What the command actually does

What has to be on your machine, and the seven steps behind sbx run.

What you need

On your machineWhat it is for

gitWorktrees and branches are driven through the git CLI
Go 1.27Only to build the binary. Nothing at runtime
A Claude Code or Codex accountUse sbx login claude or sbx login codex --import ~/.codex; credentials are shared within your dedicated daemon

That is the whole list. Your project's Node, Python or Go toolchain does not need to be on the host — it is in the image. Its control files live under ~/.sbx/; Task worktrees and branches also update the repository Git metadata. Docker volumes retain authentication and caches independently of the binary.

Choose a provider and check ownership

Use a Docker daemon dedicated to one trusted operator. Run sbx isolation status --json; adopt legacy volumes with sbx isolation adopt only after confirming that the daemon is yours. Changing SBX_HOME does not isolate Docker volumes or users.

sbx login codex --import ~/.codex   # only auth.json, not config or sessions
sbx login codex --status
sbx run --agent codex codex-fix     # select Codex without editing configuration
sbx run --agent codex codex-fix     # resume with the same provider

Without a local auth.json, sbx login codex uses device-code login. Omitting the provider from login always selects Claude. For automation, sbx version --json, sbx admit --envelope request.json and sbx run --envelope request.json provide schema discovery, read-only admission and a bounded headless run. The envelope takes its provider from configuration, not --agent.

See the automation reference for timeout, cancellation and exit codes, and the testing guide before running formal acceptance.

Seven steps behind one command

sbx is a single Go binary with no daemon and no background service. It shells out to docker and git — no SDKs — and for a task that does not exist yet, sbx run fix-login does this:

  1. Locate the workspace. git rev-parse --show-toplevel; the id is the directory name plus six hex of the path's hash, e.g. shop-e76272.
  2. Create the worktree and branch. git worktree add ~/.sbx/worktrees/<ws>/<task> -b sbx/<task>, starting from HEAD unless you pass --base.
  3. Make sure the image exists. The tag is a hash of the two Dockerfiles, the entrypoint, the Claude and Codex versions and your UID/GID — unchanged inputs reuse the image, a changed one rebuilds.
  4. Create the task's network, --internal: no route to the outside at all.
  5. Attach it to the proxy. Start the shared squid if it is not up, mint this task's username and random token, write its config fragment, squid -k reconfigure.
  6. Create the dep volumes and the container, mounting the worktree, the main repo's .git, sbx-home, sbx-cache, the state directory and a read-only /sbx/gen — and nothing else from your host.
  7. Start the selected agent in tmux. Interactive run attaches; --detach returns while the agent keeps running. Headless waits by default and stops its container on completion.

Any step that fails unwinds the earlier ones in reverse, keeping the worktree so nothing you wrote is lost.

Running the same name again is the resume path, not an error: container stopped, start it; Claude exited because you hit Ctrl-D, restart it in the same tmux session and continue the previous conversation; everything already up, just attach. So sbx run is safe to type twice.

05

Questions people actually ask

Organised by the question, not by the module.

Lifecycle — what a task creates, and what it leaves

One task from start to finish — what gets made, and who cleans it up?

Every artifact belongs to exactly one of two groups: scoped to the task, which sbx done removes, and work or expensive state, which it never touches.

ArtifactWhere it livesRemoved by done
branch sbx/<task> and its commitsyour main repo's .gitno — you delete it, after merging
worktree~/.sbx/worktrees/<ws>/<task>yes
container sbx-<ws>-<task>Dockeryes
task networkDocker, --internalyes
proxy identity + token~/.sbx/proxy/yes
dep volume (node_modules…)Dockeryes
state: status.json, events.log, gen/~/.sbx/state/<ws>/<task>yes
sbx-home — login, Claude config, memoryDocker volume, sharedno
sbx-cache — npm / pip / go / cargoDocker volume, sharedno
the imageDockerno

Nothing is written anywhere else. There is no system service, no login item, no file in /usr/local other than the symlink you make yourself.

After sbx done, how do I know nothing was left running?

Every Docker resource sbx creates is labelled sbx.ws, sbx.task and sbx.kind, which is how done finds things instead of guessing at names — and how you can check it independently:

$ docker ps -aq   --filter label=sbx.ws=shop-e76272   # containers
$ docker network ls -q --filter label=sbx.ws=shop-e76272   # networks
$ docker volume ls -q  --filter label=sbx.ws=shop-e76272   # dep volumes

All three come back empty after done; that is exactly what the acceptance test asserts. When the last task in any workspace finishes, sbx-proxy stops too.

done refuses to run while the worktree has uncommitted changes and tells you to commit first — --force is the only way to discard them.

Something went wrong. Where are the logs?

Five places, roughly in the order you would reach for them:

WhereWhat it tells you
sbx lsStatus, commits ahead, diff size, time since the last activity — usually the whole answer
~/.sbx/state/<ws>/<task>/events.logOne timestamped line per Claude hook event. The timeline of what the agent was doing and when it stopped
sbx net denied [task]What the proxy refused, in three categories; --all widens it, --since 2h narrows it
sbx attach <task>The agent's own scrollback — it is a live tmux session, so Ctrl-b then [ scrolls back through everything it printed
sbx -v <any command>Every docker and git command sbx runs, plus the configuration actually in effect. The first flag to add when sbx itself misbehaves

Codex uses its wrapper to record CodexStart, CodexExit and the exact Task session ID; it does not use Claude hooks or Claude project-memory sync. For a run you started with sbx run <task> -p "<prompt>", the whole transcript is on disk: sbx logs <task> reads it from the host, so it still works after the container has stopped (a headless run stops its own container when it finishes). An interactive agent's output lives in the tmux session instead — read that with attach while the container is up.

Volumes — what survives

If the container is deleted, do I lose the dependencies I installed and my login?

It depends which one. sbx uses three kinds of volume, with very different lifetimes:

VolumeScopeHoldsOn sbx done
sbx-homeglobal, sharedcredentials, Claude config, project memorykept
sbx-cacheglobal, sharednpm / pip / go / cargo cacheskept
…-dep-<i>per tasknode_modules and friendsdeleted

So done only removes that task's node_modules. Your login and your caches stay, which is why the next task starts fast.

What is the dep volume for? Why not just use the host's node_modules?

Because the worktree is a bind mount — whatever the container writes, your host gets. Left alone, a pnpm install inside the container would drop a set of Linux-native modules straight into your macOS directory.

The fix is mount order: mount the worktree first, then mount a volume at <worktree>/node_modules to cover it up. The container sees the volume; your copy is untouched; neither side can see the other.

[deps]
mask = ["node_modules"]    # add .venv, target, vendor, …

Logins expire. What then?

Run claude auth login in a container once more. It writes to the same sbx-home, so every task picks it up immediately — no logging in task by task. The credentials never live inside a task, which is also why done cannot delete them.

Code — where the changes went

Why can't I see the agent's changes in my repo?

They are in ~/.sbx/worktrees/<ws>/<task>/, a separate git worktree. That is deliberate: otherwise three parallel tasks would overwrite each other.

The worktree is a real directory on your host, not something inside the container. code "$(sbx path fix-login)" opens it; git diff and git log work normally. The changes reach your repo directory once you merge the branch.

To skip that layer and have changes land in the repo directory itself, omit the task name and use the main task.

Can sbx done delete my code?

No, and there are two guards. Uncommitted changes make it refuse outright and tell you to commit first; --force is the only way to discard them. Committed but unmerged work lives on the branch in the main repo's .git, so removing the worktree costs nothing.

done prints the merge command when it finishes. sbx never merges on its own — that call is yours.

Network — what it can reach

Is traffic blocked by default?

No (network.mode = "open"). But everything still goes through squid, so the logs are always there and sbx net denied always works.

To tighten it, set mode = "allowlist" or pass sbx run <task> --net allowlist: only the built-in list (Anthropic, npm, pypi, the Go proxy and so on) plus whatever you configure. That is the right setting for untrusted code.

Why open is the default

Allowlist used to be the default. In practice, when the allowlist blocked a dependency download, the agent would quietly substitute something else, keep going, and report that the tests passed.

A block that gets silently worked around is worse than no block at all, because you end up trusting a false result. So the default flipped to open, and the allowlist is there for the cases that genuinely need it.

The project needs a database, or something that only exists on the intranet. Now what?

Two mechanisms, and the order between them matters. Both are sidecars on the task's network — neither gives the task a second interface, so the container still has no default route.

ShapeWorst case if the agent runs wildMechanism
a throwaway instance in a containeryou lose a database that was disposable anyway[[services]]
an instance on your own machineyou lose your local dev data[[forward]]
a shared staging instanceother people's data, real user records, irreversible writes[[forward]] + a read-only account

[[services]] can live in the repo: it declares only name, image, env and port — no address, no credential, no host path. [[forward]] cannot: it decides where your machine connects, so it is yours to write, in your global or workspace config.

A forward resolves its target once, at start, and freezes the IP into the sidecar. sbx run prints every one of them with the address it actually reached, sbx ls marks the tasks that have them, and the task's meta.json keeps the record — so when you review that branch next week, you know it was produced against something real.

Why a forward cannot point at a public address

Because then it stops being a hole and becomes a general tunnel around squid: that traffic would obey no allowlist, land in no access log, and never show up in sbx net denied. Public hosts go through network.allow, where they stay visible.

And once a task holds real data, the thing protecting you is no longer the network. Use a read-only account or a separate schema — no network setting undoes a DROP TABLE.

Can two tasks reach each other?

No. Each task gets its own --internal network and they share none. Squid tells them apart with basic auth — the username is <ws>.<task> and the password is a random token (proxy.cred, mode 0600). Borrowing another task's identity gets a 407.

State — knowing what it is doing

Where does the status in sbx ls come from? Is it guessing?

No. The settings injected into Claude register six hooks; each event writes a line to /sbx/state/status.json, which is ~/.sbx/state/<ws>/<task>/ on your host.

StatusMeaning
runningworking
idlestopped: either finished, or waiting on you
exited(agent)Claude exited, container still up; sbx run brings it back
stopped / exited(oom)container stopped / killed for memory
The one status worth checking yourself

idle does not distinguish "finished" from "stuck waiting for a human." Combined with AHEAD 0 — not a single commit — you can be fairly sure it is parked on a confirmation.

Does closing the terminal kill the agent?

No. Claude runs in a tmux session inside the container, so closing the terminal or rebooting the host changes nothing; sbx attach gets you back.

Note that Ctrl-D exits Claude rather than detaching — to leave, press Ctrl-b, release, then d. Even so, the tmux session survives an exit, and sbx run restarts Claude and continues the previous conversation, so a slip of the finger costs nothing.

Everything else

Can it see my ~/.ssh?

No. A container has exactly this: its worktree, the main repo's .git, sbx-home, sbx-cache, /sbx/state, a read-only /sbx/gen, and a read-only copy of ~/.claude/{skills,agents,commands}. Nothing else from the host is mounted. Each task is capped at 2 CPUs, 3g of memory and 1024 processes.

How are images handled? Does every run rebuild?

Two layers: a profile layer (Debian + Go + Node + Python) and an agent layer (tmux, git, ripgrep, jq, claude-code, the non-root agent user). The tag is a hash of the inputs — both Dockerfiles, the entrypoint, the Claude and Codex versions and your UID/GID — so an unchanged input reuses the image and a changed one rebuilds by itself. The first build takes a few minutes; after that a task is up in seconds.

Claude inside the container never auto-updates; sbx upgrade rebuilds the agent layer. Existing tasks keep their old image until they are torn down and recreated — which is what keeps one task on one version for its whole life.

Is the image fixed? What if I need a different stack, or one more system package?

There is one built-in profile today, web-go. You change what is in it by editing the Dockerfiles in the repo and rebuilding the binary — they are go:embed-ed, so the binary carries them and nothing depends on the source tree at runtime:

core/assets/profiles/web-go/Dockerfile   # language runtimes, system packages
core/assets/agent-layer/Dockerfile       # tmux, git, jq, claude-code, the agent user

$ cd core && make build                 # next sbx run sees a new hash and rebuilds

Files that are injected rather than baked — the hooks, the settings sbx passes to Claude, the status line — are re-rendered into /sbx/gen on every run. Changing those takes effect on the next sbx run with no image rebuild at all.

A project can bring its own image: commit a .sbx/Dockerfile and sbx builds on it instead of a built-in profile (or point image at a registry tag). It lives under .sbx/, so it goes through sbx trust like the rest of the project config. It has to be Debian or Ubuntu based — the agent layer installs its tools with apt. And if the project declares runtime versions (.nvmrc, .tool-versions, rust-toolchain.toml…), mise installs them into a volume every task shares, so the second task to ask for the same version gets it instantly.

Does what Claude learns in the sandbox come back?

Every sbx run imports this repo's project memory from your host into the sandbox. The reverse is not automatic — sbx memory pull shows you the diff first and writes only after you confirm, marking anything edited on both sides as conflict instead of merging it.

Where it stands today

Claude Code, Codex and the v1 execution protocol are implemented (updated 2026-10-27).

Available commands: run / admit / version / isolation / attach / shell / stop / ls / path / done / drop / logs / port / net / memory / login / config / trust / prep / clean / doctor / upgrade.

Limits worth knowing up front

  • two built-in profiles (web-go, py-rust); a project can bring its own image with .sbx/Dockerfile, as long as it is Debian or Ubuntu based
  • a host proxy has to speak HTTP; a SOCKS-only proxy needs a shim of your own
  • there is no sbx merge; merging is always done by a person in the main repo
  • tasks on the same Docker daemon share identity volumes; different users need separate daemons or VMs
  • v1 reports execution results, but does not automatically deliver artifacts, merge or push
  • a service or a forward is reached by its name, not localhost — it is a different container
  • a forward carries no audit trail: squid cannot see raw TCP, which is why each one has to be declared by hand and is printed on every run
  • [[services]] containers are not counted in the memory budget sbx doctor checks

Try it on one repository

Go 1.27 and a running Docker Desktop are the only prerequisites. The first build takes a few minutes; after that a new task is up in seconds.

$ git clone https://github.com/zzjha-cn/agent_sandbox
$ cd agent_sandbox/core && make build
$ ln -sf "$PWD/bin/sbx" /usr/local/bin/sbx

$ cd ~/code/shop
$ sbx run fix-login     # branch + container + Claude Code, one command
