# 2026-10-08 · 信任确认：`.sbx/` 变了就先停下来（M2-3、M2-4、M2-5）

> 承接 [2026-10-08_config-layers.md](2026-10-08_config-layers.md)。四层配置先落地，项目层 `.sbx/sandbox.toml` 才有东西可信任。

## 一句话

`<repo>/.sbx/` 的内容和上次确认时不一致，`sbx run` 就停下来把 diff 打给你看，`sbx trust` 确认后才继续。

## 为什么需要它

项目层配置是**跟着仓库走**的：队友提交一行 `allow = [..., "exfil.test"]`，你 `git pull` 下来，下一次 `sbx run` 这台机器上的沙箱就按新名单放行了。M3-2 的自定义 Dockerfile 更直接——那是一段在你机器上构建并执行的代码。

而现实是没人逐行读别人的 diff。所以这里不是"检测恶意内容"，是**把一次本来悄无声息的变化变成一次要你点头的变化**。

M2-2 的红线（密钥字段、绝对路径）管的是"项目层不许写什么"；信任确认管的是"项目层改了什么你得知道"。两件事。

## 做了什么

```
$ sbx run api
.sbx/ 和上次信任时相比有变化：

[修改] .sbx/sandbox.toml
--- 上次信任/sandbox.toml
+++ 现在/sandbox.toml
@@ -1,2 +1,2 @@
 [network]
-allow = ["api.example.com"]
+allow = ["api.example.com", "exfil.test"]
sbx: .sbx/ 自上次信任后变过。看过上面的改动后执行：sbx trust
```

```bash
sbx trust          # 展示改动（首次则展示全部内容），确认后记下
sbx trust --show   # 只看，什么都不写
sbx trust -y       # 不询问直接记下
```

记录在 `~/.sbx/trust/<ws>.json`，按 Workspace 分开。

## 几个决定

**哈希不只覆盖内容。** 路径、是不是符号链接、大小都参与。符号链接**按链接本身记录，不跟随**——否则把 `.sbx/Dockerfile` 指到仓库外，之后换掉目标文件的内容，哈希纹丝不动，而实际构建的东西全变了。这是整个机制里最容易留的一个洞。

**快照里存内容，不只存哈希。** ≤256KB 的文本文件把正文一起存进 `trust/<ws>.json`。代价是记录文件大了一点，换来的是第二次变更时能直接 diff——不用去翻 git 历史，而 `.sbx/` 本来也未必提交了。二进制和超大文件只记哈希：变更照样发现，只是输出里写明"给不出 diff"。

**没有 `.sbx/` 的仓库一行提示都不多。** 绝大多数仓库是这样的，不该为了一个安全特性给所有人加摩擦。

**只拦 `sbx run`。** 已经在跑的容器不动，`attach`/`shell`/`ls` 也不走这条路径。检查点在 design §10.1 第 3 步：配置合并之后、碰容器之前。

**`net allow --project` 写完会顺手更新信任记录**——这次改动是用户自己让 sbx 做的，不该反过来拦住他下一次 `run`。但**只在写之前本来就是已信任状态时**才这么做：否则仓库里别人留下的、用户还没看过的改动会被一起悄悄放行。这个条件单独有测试。

## 验证

`internal/trust` 9 个测试：哈希跟内容走、跟路径走、子目录文件算数、符号链接不跟随（改目标内容哈希不变、换目标哈希变）、三类 diff、diff 带着新旧内容、二进制只报不给 diff、存取往返。

`internal/cli` 5 个：没有 `.sbx/` 不拦、首次拦住并展示内容、trust 之后放行、改动和新增文件再次拦住、retrust 不越权。

手工在一个临时仓库上走了一遍完整生命周期：没有 `.sbx/` → 新建 → `run` 被拦（退出码 1）→ `trust -y` → `run` 放行 → 改内容 → 再拦 → 新增 `Dockerfile` → 再拦。

## 还没做

- 退出码对所有拒绝都是 1，没有区分"首次"和"变过"。
- `.sbx/Dockerfile` 已经在信任范围内了，但自定义 Dockerfile 本身要等 M3-2。
- 信任记录没有过期和轮转；仓库删了之后 `~/.sbx/trust/` 里的 json 会留着。
