# sbx 项目开发环境

核心任务是替用户安排当前项目的开发沙箱，减少上手决策。固定流程：**先读项目 → 分类建议清单一次确认 → 落地配置与验证 → HTML 展示**。不要先发问卷，不让用户设计 TOML、选择 prep 语法或复述文件里已有的信息。沿用用户已有选择与授权；用户仅要求方案时不构建、不启动 task，HTML 标为方案。

## 1. 先读项目，形成建议

先读取 [项目调查与确认清单](references/project-plan.md)，执行其中的调查和版本核对。识别 Git 根、monorepo 工作范围、现有 `.sbx`、语言和包管理器声明、锁文件、CI、开发命令、Docker/Compose、配置示例及依赖的服务。只读取与开发环境相关的文件，跳过依赖目录；只记录凭据变量名或文件引用，不展示密钥内容。

同时确认当前是否能访问 Docker，以及实际 sbx 的能力。使用 Python 3.9+，以本文件所在目录为基准执行：

```sh
python3 <skill-dir>/scripts/knowledge.py probe --sbx <实际sbx路径>
```

probe 只查版本、命令帮助与知识包完整性，不读项目/用户配置、不调用 Docker。退出码 0 为匹配；2 为不匹配；1 为探测或完整性错误。匹配后读取 [配置规则](references/config-rules.md)，涉及 prep、服务、网络时读取 [依赖与网络](references/prep-network.md)，需要定制工具链时读取 [定制运行镜像](references/custom-image.md)。不要将 web-go 视为必选。

无 sbx 或知识不匹配仍先完成项目调查和建议清单。仅阻塞依赖未知语义的写入或执行；寻找配套知识或核对目标版本契约和行为，不要求用户解释技术兼容性。不得自行 seal 放行未知二进制、自动升级或下载最新版。维护细节按需查 [知识维护](references/maintenance.md)，不要把知识包维护流程作为用户的接入问卷。

## 2. 给分类清单，让用户确认

把调查结果转成一份可执行的推荐清单。每类写明 **具体建议、项目证据、拟改文件/配置层、待确认项**；没有需求的类别直接写“不需要 + 原因”，不要为了填表创造服务、prep 或网络规则。

清单必须覆盖：

- **开发范围与命令**：本次子项目、编译/测试/启动命令及入口。
- **Agent 与供应商接入**：Claude/Codex、版本、现有登录或 API 凭据引用、所需端点。优先沿用用户偏好及有效配置；项目语言不能证明必须用某个供应商。不要求两者都安装，也不擅自切换账号或模型。
- **运行镜像与工具链**：选内置 profile、已有 image 或定制 `.sbx/Dockerfile`，列出项目要求的语言/包管理器版本与系统库。
- **Prep 与依赖**：是否需要、FROM 与版本依据、安装命令、COPY/watch、secret ID、缓存/依赖目录及播种目标。
- **开发服务与本地输入**：临时 services 或已有内部实例、镜像版本、端口/地址、连接变量、forward 层，以及忽略文件的可见性。
- **网络**：分别列构建下载、运行期 Agent/API、包源和内部服务；说明域名用途、现有规则是否覆盖、是否需要新增 allow 或 forward。不把放行等同可达。
- **落地与验证**：将创建/修改哪些文件，必要的本机设置，以及准备用来验证开发环境的一条项目命令。

给出推荐方案，不并排丢出一堆无结论选项。末尾只请求用户确认整份清单或指出修改项；真正无法从文件确定且会改变方案的事项集中列出，并附推荐值。用户一句“按推荐来”即进入实施；已授权的项目选择不再重复确认。若没有先前授权，等待本轮清单确认后再写配置或启动构建。出现新的实际阻塞时只追问该项，不重启问卷。不要额外询问 HTML 语言、主题或是否需要 HTML：语言沿用用户指定或当前对话，其余采用默认展示。

## 3. 确认后配置并验证

按确认清单增量修改当前项目 `.sbx/sandbox.toml`、必要的运行/Prep Dockerfile 和已授权本机设置。写前重读文件，保留注释、无关字段和用户新增内容；重复执行不重复追加。不用 `--force` 覆盖已有模板。仅改项目配置不能消除全局/工作区的高优先级覆盖或列表并集，需检查真实来源。

Prep 的语言版本必须来自该项目，不能直接复制参考示例或 `sbx prep init` 的默认 FROM。运行镜像与 prep 的工具版本、原生 ABI、系统库、缓存布局必须协调；prep 不会交付整个文件系统。具体核对规则见 [项目调查与确认清单](references/project-plan.md) 与 [依赖与网络](references/prep-network.md)。

确认范围内连续执行配置加载、`sbx config show`、必要的构建及目标 task 验证，不把工作停在补丁或命令建议上。需要额外权限时先准备具体补丁/命令再申请，独立部分继续。不自动执行真实数据库迁移或写入，遵守 `.sbx` 的 trust 流程。

验证应覆盖：

1. 配置加载无错误、无未处理的未知字段警告；生效值和来源符合清单。
2. 需要 prep 时实际构建，核对播种计划和 warnings。`sbx prep build --check` 会构建并启动探测容器，不是静态检查。
3. 在选定入口的目标 task 中检查工具版本、依赖、服务/网络及约定项目命令。main、独立 worktree、TaskSpec 的文件可见性不同；未提交配置不保证新 worktree 可见。不要编造 `sbx exec` 等接口。
4. 只清理本次测试资源。优先新临时 task 验证；reseed 会覆盖已有依赖 volume，需有对应授权。

分别记录通过、失败、阻塞、未执行和不适用。无 Docker/真实内网时仍交付配置及 HTML，写明未验证的具体部分，不以反复提问代替可完成的工作。配置加载不证明容器可用，TCP 通过不证明业务请求通过。

## 4. 交付 HTML

按 [拓扑交付](references/topology.md) 使用内置渲染器，默认输出项目 `docs/sbx-topology.html`；已有文件先读，保留用户内容。用户明确不要时跳过，不便写入项目时使用可写产物目录。后续调整更新同一份快照。

HTML 对应本次确认清单与最终生效配置：展示基础镜像 → Agent 层 → task、独立 prep 构建 → 缓存/依赖播种、服务/forward 连接及构建/运行网络。包括配置清单、来源、版本依据和实际验证状态，未使用项说明原因，不能沿用演示数据或把配置声明画成已连通。

产物语言遵从用户明确指定，否则使用对话语言；界面、节点、详情与证据说明全部本地化，配置键、命令、路径和原始值保留。主题/密度使用默认值，只有用户主动要求时调整，不写入 sbx 配置。所有内容脱敏，支持离线打开。

最终简短回复：HTML 链接、变更文件及用途、已通过的验证、阻塞/剩余事项。不再把确认过的清单逐项问一遍。项目输入变化时重查相关部分；skill 更新本身不改当前项目的沙箱配置。
