# sbx 项目配置

将用户的开发目标转为项目共享配置和必要的本机设置，交付具体差异及实际验证结果。沿用用户已有选择与授权。仅要求方案时不启动构建或 task。

## 先确定可用知识

使用运行环境可执行的 Python 3.9+，以本文件所在目录为基准执行：

```sh
python3 <skill-dir>/scripts/knowledge.py probe --sbx <实际sbx路径>
```

脚本只探测版本和相关命令帮助，不读取项目、用户配置或凭据，不调用 Docker。返回 JSON：退出码 0 为匹配；2 为知识不匹配；1 为探测或包完整性错误。没有 sbx 时继续调查项目，交付明确的安装/验证阻塞项。

匹配后读取 [配置规则](references/config-rules.md)；涉及 prep、服务、网络或本地文件时再读取 [依赖与网络](references/prep-network.md)。项目不需要包含 sbx 源码。

不匹配时可以继续调查和准备方案，但不要用未经确认的语义写入配置或执行构建。寻找目标版本配套的知识包，或核对对应版本契约与行为。不要运行 seal 给未知二进制放行，不自动下载最新版、不升级用户 sbx。遇到 dev 构建也不能仅按版本字符串认定兼容。来源、安装、维护与验证方法见 [知识维护](references/maintenance.md)。

## 调查与对话

1. 确定当前执行位置：宿主机、受限沙箱，或无 Docker 的环境。不假设当前 agent 能管理宿主机。识别 Git 根、工作子目录和 monorepo 边界。
2. 针对性读取依赖清单、锁文件、语言版本、CI、Makefile、Dockerfile / Compose、开发说明与已有 `.sbx`。不遍历依赖目录；变量优先看示例文件或名称，不输出实际凭据。CodeGraph 可用时辅助复杂项目分析，缺失时不阻塞。
3. 给出简短摘要，区分证据确认、推断和待决定事项。数据库客户端依赖不能证明需要创建数据库。
4. 只问影响方案且尚未知的信息：要编译/测试/启动哪些内容，agent 选择，私有依赖，临时服务或已有实例，构建与运行各需哪些网络，是否依赖忽略文件。每轮聚焦相关决策，提供有证据的推荐及少量选项。
5. 不重复询问文件可确认的信息。密钥只询问环境变量名或本地文件路径，不要求用户粘贴密钥正文。

## 形成方案并修改

- 将需求映射到 profile / image、prep、services、forward 和运行期网络；规则见上述参考文件。能力不足时列出缺口，不发明配置字段。
- 先说明拟改文件、配置层、关键选择和验证命令，再完成已授权的可逆修改。需要额外权限的步骤准备好具体补丁和命令后再申请；独立可完成部分继续推进。
- 修改前重新读取文件，对相关字段做最小补丁，保留注释、无关字段和用户新增内容。优先沿用已有版本；不要无故重写全部 TOML 或 Dockerfile。不用 `--force` 覆盖已有模板。
- 检查同名服务、列表并集、高优先级覆盖。重复请求应产生相同配置，不重复追加。无法在当前层删除的设置要解释其来源。
- 只有实际需要固化依赖时创建 prep。构建步骤、凭据来源、COPY 输入、缓存和 watch 必须一致。预装系统工具需要运行镜像支持，prep 不会交付整个文件系统。
- main 和独立 task 的输入可见性不同；先核对入口，不能把 `.gitignore` 或 deps.mask 当成隔离敏感文件的通用规则。

## 验证与交付

按需求执行并分别报告：

1. 当前 sbx 加载配置，处理错误和未知字段警告。
2. `sbx config show` 核对生效值及来源；读取 prep 或组织约束有缺失提示时说明范围。
3. 需要 prep 时实际构建并检查播种计划。`sbx prep build --check` 会执行构建和容器探测，不是静态检查。
4. 在选定入口的目标 task 内检查工具链、依赖、文件、服务和网络，然后运行约定的一条项目命令。无非交互命令接口时明确使用现有交互 shell；不要编造 `sbx exec`。
5. 仅清理本次创建的测试资源。reseed 会覆盖依赖 volume，使用前确认授权范围；优先用新临时 task 验证。

分别记录已通过、失败、阻塞、未执行、不适用。写出配置不代表构建或测试通过；TCP 可达不代表认证或业务请求成功。没有 Docker 或真实内网时保留可审阅产物及具体后续步骤。

最终回复列出变更文件及目的、用户关键选择、实际验证结果和剩余事项。默认不额外写报告文件，用户需要团队说明时再写。探测仅会话内保存；项目输入变化后重查相关部分，本机配置修改前重读，skill 更新不自动改项目。
