# 先读项目，再确认开发环境清单

用于首次接入和增量调整。先从项目推导可执行方案，再让用户确认一次；已有配置也作为证据，不能把已有选择当作未知问题。

## 读取顺序与推导

| 分类 | 优先检查 | 应形成的建议 |
|---|---|---|
| 开发范围 | Git 根、项目说明、workspace/monorepo 声明、现有 `.sbx`、Makefile、CI | 目标子项目，实际编译/测试/启动命令，选用入口 |
| Agent | 用户已表达偏好、项目 agent 文档、有效 sbx 配置、已配置的登录方式/凭据引用和端点 | 推荐一个已可用的 Claude/Codex 接入；无依据时给出待确认的推荐，不凭语言选供应商 |
| 工具链 | go.mod/go.work、package.json、锁文件、.node-version/.nvmrc、pyproject.toml、.python-version、rust-toolchain.toml、mise 配置、Dockerfile、CI | 每项版本约束、选定版本与文件/字段依据；profile 是否满足，需要哪些系统库 |
| Prep | 锁文件、私有包源、安装命令、本地模块、现有 prep、deps.mask | 有价值才启用；预下载/安装哪些依赖，使用什么基础层，如何播种 |
| 服务 | Compose、开发配置示例、测试夹具、应用初始化代码 | 区分本地临时服务、宿主机服务、已有远程实例；镜像版本、连接变量和 readiness |
| 网络 | 包源配置、锁文件中的下载主机、私有模块、API 客户端配置、Agent 接入端点、现有网络规则 | 逐项列用途与阶段；现有覆盖、新增 allow、forward 或待确认地址 |
| 文件与凭据 | .gitignore、配置示例、证书引用、本地依赖、已有 secret 映射 | main/worktree 可见性；只记录变量名、secret ID 和路径，不收集密钥正文 |

不要遍历 node_modules、vendor、.venv、构建输出或读取整份含真实凭据的 env 文件。缺少信息时先读示例、引用位置及变量名。不要为了选 Agent 发起真实模型请求、购买服务或读取凭据正文。

## 版本核对：运行环境与 Prep 必须成对安排

1. **先分清约束与固定版本。** Go 的 `go` 是最低语言要求，`toolchain` 是工具链建议；结合 CI、mise 与项目开发文档判断实际使用版本。Node 的 engines 是范围，packageManager 或锁文件决定包管理器；Python 同时核对 requires-python、版本文件和锁文件。锁文件格式版本不是运行时版本。
2. **有冲突就定位具体冲突。** 项目明确的固定开发版本优先作为候选，检查它是否满足其余约束；CI 矩阵不一定是本次开发版本。不能满足时在清单中指出文件、值、影响和推荐处理，不静默选择最新或较低版本。
3. **列出版本配对。** 在确认清单中写“项目要求 → 运行镜像工具版本 → prep 工具版本 → 依据”。内置 profile 不满足时选符合要求的 image/自定义 Dockerfile，不为继续用 web-go 降低项目要求。原生扩展还需核对 OS、架构、Python/Node ABI、libc 和系统库。
4. **模板是结构参考。** 当前内置 prep 初始化模板含 `FROM golang:1.23`，不是项目推荐版本，也没有自动解析项目工具链。不要直接生成并照用；若使用 init，必须按项目修正 FROM、WORKDIR、安装命令、缓存位置及 COPY/watch。参考文件中的 `golang:1.27` 同样只是示例。无需 init 时直接生成合适 Dockerfile。
5. **按锁文件安装。** 采用项目自己的包管理器与 CI 安装方式，保持锁文件；不混用 npm/pnpm/yarn，不默认加 `--ignore-scripts` 破坏原生构建，不通过升级依赖解决环境配置问题。Go 缓存显式对齐 GOMODCACHE；Python venv、Node 原生模块等应在兼容路径/环境下生成。
6. **文件生成后再核对。** 对照最终 FROM、命令、COPY/watch、secret ID 和播种目录，确认与清单一致；运行镜像和 prep 构建成功后，分别检查实际工具版本，新 task 中再验证依赖和项目命令。尚未构建就写“所选版本，待验证”，不声称存在/拉取成功；需要确认外部镜像 tag 时使用可信镜像源查询或实际拉取结果，不凭空承诺。

运行工具/系统库放运行镜像；依赖种子/缓存放 prep。默认不额外创建 prep：小型公开依赖可沿用正常安装；私有依赖需在宿主构建阶段获取、或预装明显降低启动成本时说明收益再启用。数据库客户端依赖不证明要起数据库，锁文件里的下载域名也不证明运行期都需要放行。

## 一次确认的呈现方式

按以下格式，填入实际文件、版本、主机与命令。每行应有结论；不提供一堆让用户重新设计的选项。

| 分类 | 推荐安排 | 项目依据 | 拟改位置 / 待确认 |
|---|---|---|---|
| 开发范围 | 目标子项目与验证命令 | Makefile/CI 的实际目标 | task 入口 |
| Agent/供应商 | 沿用已选 Agent、版本和登录/端点；无需安装另一 Agent 时明确说明 | 既有偏好与有效配置 | 项目 default_agent；敏感接入在本机层 |
| 镜像/工具链 | 具体 profile/image/定制 Dockerfile，版本及系统库 | 项目版本声明及开发环境 | `.sbx/sandbox.toml` / `.sbx/Dockerfile` |
| Prep | 需要时列基础镜像、依赖步骤、watch、缓存/播种目录和 secret ID；否则给出不需要的原因 | 锁文件及私有包源 | `.sbx/prep.Dockerfile` 与 prep 字段 |
| 服务/本地文件 | 临时实例或复用现有实例，镜像/端口/连接变量；必要的文件可见性安排 | Compose/开发配置/忽略规则 | services 或本机 forward；缺失地址才待确认 |
| 网络 | 逐个列构建包源、Agent/API 与内部目标；现有覆盖与新增规则 | 端点配置、包源、当前网络模式 | 项目 allow / 本机 upstream / forward |
| 验证/交付 | 配置加载、构建、task 内项目命令、HTML 路径 | 上述开发目标 | 真实权限或环境阻塞 |

结尾示例：“以上是根据项目整理的推荐方案。确认后我会写入这些配置、构建验证并生成 HTML；你可以回复‘按推荐来’，或只指出要调整的项。”

如果内网服务地址/认证引用确实无法确定，将这一个缺口附在对应行，不问泛泛的“你需要哪些服务/网络/prep”。不要把供应商账号缺失、Docker 不可用或版本冲突藏在已确认的结论里。已确认清单后，配置和 HTML 都沿用相同选择；验证失败只修相关项，改变已确认的供应商、版本或连接目标时说明差异。
